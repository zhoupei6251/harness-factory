# 错误处理与稳定性保障手册

> 本文档是 `douyin-script-optimizer` skill 的**错误处理权威参考**。
> 当工作流任何环节出现异常时，按本文档定位错误码、理解原因、执行修复步骤。

|--------|--------|---------|-------------|

| E008 / E009 | 分镜脚本不合格（太泛/没标来源） | 把画面写具体（≥15字+具象名词），source 填 ai_gen/asset_pool | ✅ 自动重新校验 |

| E014 | 重试两次还不行，放弃自动 | 改要点/降温度/换模型后手动重来 | ✅ 手动完成后继续 |
| E015 | 踩了合规红线（极限词等） | 按提示改掉违规表述再继续 | ✅ 改后自动继续 |

## 二、每个错误的详细处理

### Node A 调用失败（E004）

**现象**：Dify 显示"请求超时"或"模型服务错误"，Node A 无输出。

**按顺序排查**：

| 步骤 | 排查动作 | 预期结果 | 若不符则… |
|------|---------|---------|-----------|
| 1 | 检查 Dify 中配置的 API Key 是否过期 | Key 有效 | 重新生成并更新 Key |
| 2 | 检查模型服务商账户余额 | 有余额 | 充值 |
| 3 | 在终端测试网络连通性：`curl -I https://api.openai.com` （或对应厂商） | HTTP 200 | 检查代理/防火墙设置 |
| 4 | 确认模型名称拼写正确（如 `qwen-plus` 非 `qwen`） | 名称匹配 | 改为正确名称 |
| 5 | 降低 `max_tokens` 参数（如有设置） | 不超模型上限 | 减到 4096 或更低 |

**超时保护配置（预防 E004）**：

```
推荐超时设置（在 Dify LLM 节点或外部编排层配置）：

Node A（含延展+优化，输出较长）：
  - 连接超时: 15 秒
  - 读取超时: 120 秒（长文案生成需要时间）
  - 总超时: 180 秒

Node B（仅标题，输出较短）：
  - 连接超时: 10 秒
  - 读取超时: 60 秒
  - 总超时: 90 秒
```

**重试策略（指数退避）**：

```
第 1 次失败 → 等 3 秒 → 重试
第 2 次失败 → 等 8 秒 → 重试
第 3 次失败 → 报错 E004，不再自动重试 → 提示用户检查上述 5 步
```

### Node A JSON 解析失败（E005）

**现象**：Node A 返回了文字但 JSON 解析报错，或关键字段缺失。

**常见原因与修复**：

| 原因 | 表现 | 修复方法 |
|------|------|---------|
| 模型输出混入了 ```json 代码块标记 | 外层有 markdown 包裹 | 在 Node A 后加代码节点：正则去除 ```json ... ``` 包裹后再解析 |
| temperature 过高（>0.9）导致输出发散 | 输出包含解释性文字、不在 JSON 内 | 将 Node A temperature 降到 0.6–0.7 |
| 输出被截断（max_tokens 不够） | JSON 末段截断，shot_plan 不完整 | 提高 max_tokens 到 4096+；或在 Prompt 里要求"先输出 shot_plan 再输出其他字段" |
| 模型能力不足（<7B 开源小模型） | 结构经常性错乱 | 换 qwen-max / DeepSeek V3 / GPT-4o |

**防御性代码（Dify 代码节点可加）**：
```python
import json, re

raw = raw_output  # Node A 原始文本输出

# 1. 去除可能的 markdown 代码块包裹
cleaned = re.sub(r'^```json\s*', '', raw.strip())
cleaned = re.sub(r'\s*```$', '', cleaned)

# 2. 尝试解析
try:
    data = json.loads(cleaned)
except json.JSONDecodeError as e:
    # 3. 尝试提取最后一个完整 JSON 对象（模型可能在 JSON 后追加了解释）
    last_brace = cleaned.rfind('}')
    if last_brace > 0:
        try:
            data = json.loads(cleaned[:last_brace+1])
        except:
            raise Exception(f"E005: JSON 解析失败，错误位置: {e.pos}. 原始片段: {cleaned[max(0,e.pos-30):e.pos+30]}")
    else:
        raise Exception(f"E005: 无法从输出中提取合法 JSON")
```

### shot_plan 校验失败（E008 / E009）

**现象**：Node A 返回了合法 JSON 但 shot_plan 不满足硬约束。

**E008 — visual_prompt 太泛的判定规则**：

以下情况**视为不合格**（触发 E008）：
- visual_prompt ≤ 14 个汉字
- visual_prompt 不含任何具象名词（如"办公桌""咖啡杯""手机""箭头""评论气泡"）
- visual_prompt 包含禁用短语："相关画面""对应场景""合适素材""配合口播"

**合格的 vs 不合格对照**：

| ❌ 不合格（触发 E008） | ✅ 合格 |
|-----------------------|--------|
| "相关画面" | "手机屏幕特写，显示播放量卡在500的抖音创作者后台界面" |
| "办公室场景" | "冷色调办公室背景虚化，桌上散落着草稿纸和一杯凉掉的咖啡" |
| "配图" | "算法赛马示意图——多条赛道上的赛马动画，领头马金色高亮" |
| "数据图表" | "柱状完播率对比图，左侧红色矮柱（低完播），右侧绿色高柱（高完播）" |

**E009 — source 为空的修复**：
- 如果你有该画面的真实素材 → 填 `asset_pool`
- 如果没有、需要 AI 生成 → 填 `ai_gen`
- 系统不允许留空，这是硬约束

**自动化校验（Dify 代码节点）**：
```python
import json

data = json.loads(node_a_output)
errors = []

for i, beat in enumerate(data.get("shot_plan", [])):
    vp = beat.get("visual_prompt", "")
    src = beat.get("source", "")
    
    if len(vp) < 15:
        errors.append(f"槽{i+1}({beat['beat']}): visual_prompt 仅{len(vp)}字，需≥15字")
    
    # 检测是否含具象名词（简单启发式：至少一个常见具象词）
    concrete_words = ["屏幕", "手机", "桌面", "咖啡", "图表", "人", "手", "箭头",
                      "按钮", "气泡", "界面", "背景", "图片", "视频", "文字", "数据"]
    has_concrete = any(w in vp for w in concrete_words)
    if not has_concrete:
        errors.append(f"槽{i+1}({beat['beat']}): visual_prompt 缺乏具象描述")
    
    if not src or src.strip() == "":
        errors.append(f"槽{i+1}({beat['beat']}): source 为空，须填 asset_pool 或 ai_gen")

if errors:
    raise Exception(f"E008/E009: shot_plan 校验不通过:\n" + "\n".join(errors))
else:
    print("✓ shot_plan 全部通过校验")
```

### Node B 输出异常（E011）

**现象**：Node B 输出的 title_options 不是 5 个元素的数组。

**排查与修复**：

| 检查项 | 正常值 | 异常处理 |
|--------|--------|---------|
| `title_options` 是 list？ | 是 | 如果是 string，尝试 `json.loads()` 解析 |
| `len(title_options)` == 5？ | 是 | 如果 >5 取前5个；如果 <5 触发 Node B 重跑 |
| 每个元素是 str 且非空？ | 是 | 过滤空元素后补足到5个（重跑优先） |
| `tags` 存在且是 list？ | 是 | 如不存在，设为空列表 `[]`（非阻塞） |

**Node B 重跑策略**：
- 第 1 次 title_options 异常 → 自动重跑（temperature 微调 +0.05）
- 第 2 次仍异常 → 报错 E011，附带 Node B 的原始输出供人工检查

### 变量引用丢失（E013）

**现象**：导入 DSL 后，Dify 画布中变量显示为红色/未解析。

**逐步修复**（配截图描述）：

1. 打开 Node A 的 LLM 节点编辑器
2. 在 Prompt 文本中找到所有 `{{#start.xxx#}}` 格式的引用——它们应该显示为**蓝色/紫色高亮变量标签**
3. 如果显示为纯文本（未高亮）：点击该位置 → 从右侧「变量」面板拖入同名变量
4. 对 Node B 中的 `{{#node-a.optimized_script#}}` 和 `{{#start.xxx#}}` 引用重复同样操作
5. 保存后再次运行

**版本兼容性表**：

| Dify 版本 | DSL 变量语法 | 本模板兼容性 |
|-----------|-------------|------------|
| v0.6.3+ (2024下半年+) | `{{#xxx#}}` | ✅ 完全兼容 |
| v0.3.x – v0.6.2 | `{{xxx}}` | ⚠️ 需手动改语法 |
| Cloud SaaS 最新版 | 双语法都支持 | ✅ 兼容 |

## 三、超时保护与稳定性配置（解决 R-运行稳定性 4.3）

### 推荐的超时配置

| 节点 | 建议连接超时 | 建议读取超时 | 最大总超时 | 说明 |
|------|-------------|-------------|-----------|------|
| **开始节点校验** | 5s | 5s | 10s | 只是变量校验，很快 |
| **Node A（含延展分支）** | 15s | 120s | 180s | 最重的节点，需要足够时间 |
| **Node A score 判断** | 5s | 5s | 10s | 条件判断，很快 |
| **Node B 标题生成** | 10s | 60s | 90s | 比 Node A 轻 |
| **JSON 校验节点** | 5s | 10s | 15s | 代码执行，很快 |
| **TTS 调用（下游）** | 15s | 60s | 90s | 百炼 API 通常稳定 |

### 降级策略

当某个节点持续失败时的降级路径：

```
正常路径: Node A → (score≥7) → Node B → 完成
                    ↓ (score<7, 重试2次)
降级路径: Node A → (score仍<7) → 输出 + 质量预警标志 → 人工审核后放行
                    ↓ (Node A 完全不可用)
最终降级: 使用缓存的上一次成功结果（如果有同主题缓存）→ 标记"使用缓存版本"
```

### 监控指标建议

如果在外部编排层（如 Python 脚本/n8n）调度 Dify 工作流，建议记录以下指标：

| 指标 | 记录方式 | 告警阈值 |
|------|---------|---------|
| 单次端到端耗时 | 每次运行记录 start→end 时间 | >5min 告警 |
| Node A 平均耗时 | 记录每次 Node A 执行时间 | >120s 告警 |
| score 分布 | 统计 score 直方图 | 连续 5 次 <7 告警 |
| 重试率 | 重试次数 / 总运行次数 | >30% 告警 |
| JSON 解析成功率 | 成功解析 / 总调用 | <95% 告警 |

## 四、用户自助诊断流程图

当遇到问题时，按此流程自检：

```
遇到问题？
  │
  ├─ ① 是导入/配置问题吗？（DSL 导入失败、变量红显）
  │     → 查 E013（变量引用丢失）
  │
  ├─ ② 是输入问题吗？（运行即报错）
  │     → 查 E001-E003（输入校验类）
  │     → 先看是不是 key_points 为空或太泛
  │
  ├─ ③ 是 Node A 输出问题吗？（跑了但 score 低 / JSON 报错）
  │     → score 低：查 E006/E007/E014（质量门类）
  │     → JSON 报错：查 E005（解析类）
  │     → shot_plan 不合格：查 E008/E009（声画类）
  │
  ├─ ④ 是 Node B 输出问题吗？（标题不对）
  │     → 查 E010/E011（标题类）
  │
  └─ ⑤ 是下游对接问题吗？（TTS / 剪映）
        → 下游 TTS 字符清洗见 video-render-engine 的百炼配音章节
        → 查 workflow-guide.md 第 9 节
```

## 五、常见误区（反模式补充）

这些是用户最容易犯的错误，每一条都来自真实踩坑经验：

| ❌ 反模式 | 为什么错 | ✅ 正确做法 |
|----------|---------|------------|
| key_points 只写 1 条笼统的 | 模型延展方向不受控，产出空洞 | **必须 3–5 条具体、有立场**的要点 |
| raw_script 和 topic/key_points 都为空 | Node A 不知道要做什么 | 至少提供其中一种输入源 |
| video_duration 填 300（5分钟） | 口播 5 分钟 ≈ 1350 字，远超单轮 LLM 输出上限 | **控制在 15–120 秒**，长内容拆成系列 |
| Node A temperature 设 1.0 | 输出发散，JSON 结构不稳定 | **0.6–0.7** 平衡创意与结构 |
| 跳过 shot_plan 直接用随机素材 | 声画不匹配拉低完播率，被判低质 | 必须 shot_plan 驱动选片/生图 |
| quality gate 只判不重跑 | 低分内容直接流入下游污染 TTS/剪映 | **score<7 必须反馈重跑**（最多2次） |
| 不同 video 用不同 style_anchor | 同账号系列视频风格跳来跳去 | 同系列共享同一个 style_anchor |
| TTS 合成后不验证时长 | 估算偏差 ±10s 很常见，直接对齐剪映会声画错位 | **以实际音频时长为唯一基准**回写 beat |
